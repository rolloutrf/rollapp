# Rollapp workspace instructions

## Central design-system ownership

- List and day tiles share `ListTileContent` and `data-list-tile` CSS in `src/index.css`; never duplicate inline tile geometry or label/count font styles. Page actions retain 24px padding on both sides even with inline icons or loading spinners.

- Follow `docs/design-system.md` for the shared shadcn Base Nova component/role map. Similar elements must share their role owner, geometry, state styling and keyboard/focus behavior. Change that owner and all consumers together; update the contract and its full checks. Keep product variants outside upstream primitives.
- All in-flow page toolbar text actions, including list/group settings and imports, use `PageActionButton`; never restore a local Button `shape` prop or per-page height/padding/radius. `test:ui` guards this API and `test:action-rails` checks real contact/Wishlist/education headers.
- Full consistency audits include `test:contact-notes` through `check:comprehensive`; partial case/viewport or report-review settings are diagnostic only.

- Horizontal tile rails must match the main Wishlist edge treatment. Compose
  Wishlist/group navigation and day ribbons with `horizontal-tile-scroller`;
  keep gutters, clipping, scrollbar and edge behavior centralized in
  `src/spacing.css`. Use native hard clipping, without fading masks, gradients
  or overlay veils. Change shared behavior centrally rather than adding local
  per-page treatments. Preserve each rail’s selection and keyboard behavior.

- Never paint the application or public-profile header background. Keep the
  header transparent on every route, theme, viewport and scroll state: no solid
  or translucent fill, gradient, backdrop blur, shadow, or painted pseudo-element
  underlay. Individual buttons/selects retain their semantic surfaces. Preserve
  this rule when changing navigation; verify computed header background and
  backdrop-filter in the navigation smoke matrix.

- Empty inline-block hints decorate only the current collapsed text caret's
  textblock, including nested lists/cells/columns/captions. Retire old hints on
  selection-only changes without document/history/save writes. Keep each hint
  on one bounded ellipsized line so it cannot paint over neighbouring prose.
  Verify the eight-viewport placeholder cases and full text/comprehensive suite.

- Image viewing in shared rich editors/readers is non-authoring: preserve exact
  image/figure/caption attrs, native image role and authored alt accessible name,
  native selection, history and save queues. Compose
  FullscreenDialog/ControlBar and the shared VisualViewport, never a separate
  focus trap. Retire on document/source/selection/access/IME/lifecycle changes;
  restore focus only after explicit dismissal with a still-valid owner. Keep
  loading/disabled and competing block/table/column/resize guards. Run full
  text-edit/comprehensive; image-reader-only is diagnostic, not release evidence.

- Rich image captions are real inline content in the shared document/history/save
  queue, separate from alt/title. Preserve the original image attrs inside one
  figure/caption movement unit; normalize only explicit child image NodeSelection
  to that figure, never native text ranges. Cut/Delete must not leave an empty-src
  required image filler. Keep read-only/IME/source guards, canonical reload,
  selected spaces/marks, separate creation/typing/paste Undo and shared caption
  typography. Tiny media retain readable captions without descendant clipping.
  Verify native clipboard, protected questions, draft/retry, resize capture and
  full editor/comprehensive before integration; branch-only targets are not release.

## Database

- Keep the shared production PostgreSQL connection budget: `PG_POOL_SIZE=2` in the production Compose and `PG_POOL_SIZE=1` per persistent development preview. Follow `docs/database-connections.md`; never size each checkout as if the role limit were private to it. Preserve configured production/TLS/verify mode and keep managed previews running after changes.

- Always use the repository's configured production database for Rollapp development, previews, diagnostics, and verification.
- Never silently substitute an in-memory, demo, mock, or local database when the production database is unavailable. Report the connection problem instead.
- Keep the production development connection running between tasks. Use direct TLS access by default; use the SSH tunnel only when `ROLLAPP_DATABASE_CONNECTION=tunnel` is explicitly configured. On this Mac, `npm run dev:keepalive` enables the persistent service and `npm run dev:keepalive:status` checks it. Do not stop it after verification unless the user asks.
- If sandbox restrictions prevent network or process checks, repeat the check with the required permissions. An unavailable process inspection is not proof that a PID is stale; never remove a live service's PID file on that basis.
- Connecting to the production database does not by itself authorize destructive schema changes, bulk data mutations, or data deletion. Require an explicit user request for those operations and verify the exact target first.
- Production development startup uses `ROLLAPP_DATABASE_INITIALIZATION=verify`: check the existing auth/document schema in a READ ONLY transaction, retain the reserved-username guard, and never run migrations, data backfill, or reservation cleanup just to reload application code. Keep missing-schema/connection errors visible without a demo fallback.
- Ordinary production releases also set `ROLLAPP_DATABASE_INITIALIZATION=verify` in the deployment template. Preserve its unit guard and run the real existing-schema read-only check before rollout. Schema migrations, backfills and reservation cleanup require a separate explicitly authorized operation, not an ordinary UI deployment.

## Typography

- Treat `src/typeset.css` and the typography tokens in `src/index.css` as the implementation source of truth for Rollapp typography. Keep the human-readable contract in `docs/typography.md` synchronized with them.
- Use `Geist Variable` (`--font-sans`) for body copy. Use `--font-heading` for headings; it currently resolves to the same family. Do not introduce another font family without an explicit design requirement.
- Wrap readable content pages in `typeset typeset-rollapp` instead of recreating heading, paragraph, list, link, caption, and vertical-rhythm styles in individual components.
- Add `typeset-document` to a nested semantic article whose sections and headers need their first text block trimmed independently of the surrounding page shell. Mark a non-semantic prose wrapper with `data-typeset-group` to trim its first block without introducing a spacer.
- Follow the shadcn/typeset rhythm contract: `--typeset-size`, `--typeset-leading`, and `--typeset-flow` are the only prose rhythm inputs. Derive heading, paragraph, list, quote, media, table, and divider spacing from them.
- Prose spacing flows in one direction. Text blocks may set `margin-block-start`; keep `margin-block-end: 0` and do not add empty spacer nodes. Avoid forward-looking `:last-child`, `:has()`, and `:empty` selectors in typography layout rules.
- A heading owns the tighter gap to the block that follows it. Do not recreate heading bottom margins or combine a preceding bottom margin with a following top margin in page CSS.
- Keep shadcn component compositions outside prose styling with `not-typeset` or `data-not-typeset`. Let the component's official padding and gap contract control its internals.
- In component compositions, use `flex`/`grid` with `gap-*` for sibling spacing; do not use `space-x-*` or `space-y-*`. Keep spacing on the parent instead of distributing margins across children.
- Keep the primary Rollapp body text in `Geist Variable`, regular `400`, normal style, zero tracking, and `--foreground`. Use `1.125rem/1.75rem` (`18px/28px`) at every viewport size. Paragraphs and list items use `text-wrap: pretty`.
- Apply the `18px/28px` primary body contract throughout the application, including Wishlist surfaces. Use `typeset typeset-rollapp` for readable content and `rollapp-body` for non-prose or portalled surfaces such as authentication, profile settings, contact details, and generic error pages. Components may use the shared caption, label, heading, or control roles when their semantics require a different size.
- Keep the semantic heading scale defined in `src/typeset.css`: h1 `2.25rem/2.5rem`, h2 `1.875rem/2.25rem`, h3 `1.5rem/2rem`, h4 `1.25rem/1.75rem`, h5 `1.125rem/1.75rem`, and h6 `1rem/1.5rem`.
- Use the shared caption token (`0.8125rem/1rem`) for captions and secondary microcopy. Use the shared uppercase label treatment (`0.8125rem/1rem`, weight `600`, tracking `0.08em`) for eyebrows and section labels.
- Block quotations, including theses, retain italic text and the shared start padding without a vertical border in reading or inline editing.
- Preserve the product-level Large control contract in `src/index.css`: primary application controls and menu/select rows use the primary `1.125rem/1.75rem` (`18px/28px`) text and at least `3rem` minimum block size. Keep upstream shadcn primitives at their official Base Nova defaults and apply product sizing in the composition/global product layer.
- Prefer semantic HTML and the shared typography preset or Tailwind theme tokens over arbitrary values such as `text-[…]`, local `font-size`, or local `line-height` declarations.
- Do not add a new one-off type size merely to match a single screen. Reuse the closest semantic role; if a genuinely new role is needed, add and document it in the shared typography source first.
- Component-specific overrides are allowed only when the content has a distinct semantic role or a verified responsive constraint. Keep the exception local and avoid changing the global scale to fix one component.
- When changing shared typography, verify both desktop and mobile layouts and run the relevant UI checks, including `scripts/check-shadcn.mjs` and affected visual smoke coverage.

## Responsive layout and visual consistency

- Treat `src/spacing.css` as the source of truth for page gaps, insets, and chrome spacing; `src/containers.css` for width roles; and `src/overlays.css` with `src/hooks/use-visual-viewport.js` for portalled surfaces. Keep `docs/spacing-system.md`, `docs/container-system.md`, and `docs/mobile-overlays.md` synchronized when those contracts change.
- Use the existing `app-page`, `page-stack`, `page-toolbar`, and container-width roles before adding local dimensions. A width role is a maximum, never a fixed page width. Apply the page inset once: 16px through 640px, 24px from 641–1180px, and 32px above 1180px. The app shell adds its own 16px inset above 820px; account for it instead of duplicating it.
- Align ordinary page content and the global header to `--layout-page-width` and `--layout-page-inset`. Page-level horizontal collection/action rails always reach the viewport edges on mobile and desktop; their gutters belong inside the scroll owner, never an inset clipping ancestor. Planning boards retain their own full-bleed scroll owner.
- Keep page action groups (`.horizontal-action-scroller`, including edit and business/store controls) horizontally centred whenever they fit, with equal inner page gutters. At every viewport width their scroll viewport reaches both screen edges; overflowing groups start at the leading gutter and remain entirely reachable by horizontal scrolling. These page actions stay in document flow and scroll vertically with the page; do not make them fixed/sticky or tie their alignment to scroll position. Keep this contract in `src/spacing.css` and `docs/spacing-system.md`, and run `node scripts/action-rails-smoke.mjs` when changing these controls or their containers. Verify icon-only, mixed, dynamic, overflow and vertical-scroll states.
- Calendar tasks with a date but no explicit time use consecutive free 30-minute display slots per day starting at 10:00, after expanding recurrences. Reserve explicit appointments first; never stretch untimed To Do items over 24 hours or mutate stored schedules during rendering. If no complete slot remains, keep the task visible in the unscheduled list.
- Calendar timeline move/range/resize share one guarded pointer owner. Preserve the original grab point, authored minutes and duration; snap gesture deltas to 15 minutes and auto-scroll the timeline viewport at its edges. Cancel outside the visible grid, on Escape/capture loss/source or period changes; never persist a no-op. Keep long-event titles visible while scrolling their interval and preserve their painted offset in body previews. Touch on event bodies retains native scrolling, with separate resize handles and the date/time form alternative. Run the complete `npm run test:calendar` and `npm run test:drag-drop` matrices.
- In daily To Do below 768px, do not render the circular date ribbon or reserve space for it. Use one top row with Previous day, a flexible date picker labelled with date and weekday, Next day, and circular Add. Use --layout-control-size (48px) for both top controls and the mobile planning bottom row, with 8px gaps; day changes preserve the selected list; use the bottom navigation selector for dedicated To Do lists and their creation. Keep the selected list in the space URL parameter and retain the date when switching or creating a list. The task list and Add action share one vertical scroll owner and must scroll entirely above the bottom navigation. The mobile Add action precedes the list and opens the shared TaskEditor via MobileFormPages, carrying the selected date and first incomplete column. Do not restore an inline mobile composer or emulate a full-height modal. Save returns only after success; page/browser Back cancels and restores the selected day. Preserve the desktop top ribbon as standard content tiles (130×100px, 18px corners, weekday and full month name above the date number), using shared `[data-list-tile]` styles outside ControlBar; navigation controls remain 48px. Run `node scripts/daily-todo-ribbon-smoke.mjs` when changing this arrangement.
- Put sibling spacing on the parent with flex/grid `gap`; give shrinking flex/grid children `min-width: 0` and scrolling children `min-height: 0`. Do not fix overflow with empty spacers, unrelated negative margins, or root-level clipping that hides inaccessible content.
- Content tabs wrap and grow vertically without internal scrolling. Wishlist list navigation is the deliberate exception: it stays on one horizontally scrollable row, reaches both viewport edges, and must not clip vertically. On phones, Kanban columns become sections of one vertical checklist; wider screens use the board scroller. Give each axis one intended scroll owner.
- Card drag previews preserve source geometry and the original grab point outside their page CSS. Require confirmed group intent before grouping; cancel outside the source grid, on Escape/capture loss/access or collection changes without saving. Keep touch scrolling on the card and use the shared 48px drag handle for education/workout touch drags. Follow `docs/drag-and-drop.md` and run the complete `npm run test:drag-drop` matrix; it is required in `check:release`.
- Wishlist group names truncate with an ellipsis on the text element inside the title button. Keep the full name accessible and available in `title`, use the full card width, and let metadata height follow content so the count stays inside the card. Run `npm run test:wish-groups` for changes to this composition.
- Keep primary controls at least 48px tall and allow action groups to wrap or reflow before controls collide. Use shared shadcn primitives and product variants. When combining `buttonVariants` with local size or radius classes on a `Link`, merge conflicting utilities with `cn` and verify the rendered shape.
- On desktop from 768px, planning space selectors (To Do lists, calendars and Kanban boards) belong to the shared top application header, in the same position as the main-page section selector. Render exactly one selector, open its menu downward and reserve the shared header height in planning content. Below 768px retain the bottom planning selector and upward menu.
- All top and bottom navigation controls use `ControlBar` from `src/components/control-bar.jsx`. Its one `--layout-control-size` token in `src/spacing.css` is 48px on every viewport, sphere, planning view and native form/detail page. Icon controls declare `data-control-icon` and remain 48×48px; control glyphs are 20px. Calendar view tabs and their outer rail are also 48px, without extra rail padding. Do not introduce separate navigation/planning sizes, responsive size changes, or local token overrides. ControlBar owns geometry; existing page shells own positioning, centering, scrolling and safe areas. Calendar grid cells, content rows, avatars and multiline form actions retain their semantic layouts; they must not redefine navigation sizes. Run `npm run test:controls` and the affected navigation/form smoke tests. The control geometry check is mandatory in `check:release` and the deployment workflow; do not skip it or replace its assertions with minimum-size checks.
- Mobile detail pages use `ContentPageActions` to put Back, the flexible accent action and overflow in one fixed bottom row: 48px height, 48px icon circles and 8px gaps, with the shared safe area/VisualViewport position. Keep fulfillment and guest copy actions available in overflow when marketplace search or reservation is primary; catalog details without overflow use Back and the primary action. Use compact labels with complete accessible names instead of wrapping this row. Content must scroll entirely above it; desktop actions stay in the content. Run `npm run test:details`, which is required by `check:release`.
- Match visible control bounds as well as DOM geometry. Keep product button/toggle backgrounds clipped to `border-box` in `src/index.css`; the primitive's `bg-clip-padding` otherwise makes a 48px filled control visibly 46px beside a 48px outline. Preserve upstream primitives. `test:controls` must retain its screenshot-pixel assertions and DPR 3 mobile coverage, along with 48px boxes, 20px glyphs and 18px/28px control text.

Keep the disabled/enabled distinction and verify opacity/background alpha in `test:form-actions`; do not modify the upstream button primitive's disabled defaults.

Preserve timezone-safe local-date keys, Russian labels and keyboard access. Run `npm run test:dates` (required in `check:release`) and the affected form/To Do smoke checks.
- Make the whole visible calendar tile or row interactive when it represents one destination, while preserving independent actions inside it, keyboard access, focus indication, and semantic labels.

Anchor contextual menus to the real native selection in isolated body portals, never to another editor or a positioned document ancestor; keep an 8px gap, flip/shift within the visible viewport, update on scrolling/VisualViewport changes and hide when the selection is offscreen. Preserve Markdown semantics, typed symbol shortcuts, selection/undo, IME, links, drafts on save failure and read-only/loading/access guards. ## Verification and durable instructions

- Follow `docs/verification.md` for the current check matrix, commands, read-only live review, release and recovery procedure. Keep this runbook and the source-specific UI documents synchronized with changes; dated audit reports are evidence, not replacement contracts.
- Record the tested commit and dirty state, commands, results, fixed findings and unverified cases in a dated report. Preserve unrelated workspace edits and inspect the final diff. Never report a build alone as comprehensive UI verification or a partial viewport filter as a complete matrix.
- Review dependencies with both `npm audit` and `npm audit --omit=dev`. Keep tooling such as the shadcn CLI in devDependencies, update compatible fixes with the lockfile, and rerun affected checks; do not force incompatible downgrades merely to clear an audit warning.
- Keep a healthy deployed version available when image reconciliation stalls. Never automatically restart a healthy-but-stale VM: first verify its identity, free disk space, image pull errors and rollback image. Keep at least 5 GB free on the current 19 GB boot disk before a manual restart/pull. Remove only explicitly reviewed unused Rollapp image tags, preserving current/rollback and all container-referenced images; no force, container/volume deletion or broad prune. Deployment is complete only when production health reports the exact expected SHA and affected UI has been checked.

- All fixed or sticky action buttons must be round (icon-only) or pill-shaped (text); compose them through `ControlBar`.
