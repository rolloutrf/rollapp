# Личные сообщения Rollapp

`/app/messenger` — список диалогов и поиск зарегистрированных участников;
`/app/messenger/:conversationId` — личный разговор. На компьютере кнопка над планированием открывает компактный Popover
поверх текущей страницы: сначала список, затем выбранный чат в том же окне.
Back возвращает к списку; крестик, Escape и клик снаружи закрывают окно.
Прямые desktop-ссылки /app/messenger открывают это окно поверх Wishlist.
На телефоне остаются отдельные страницы списка/чата.
Иконка над планированием использует общий 48px ControlBar и промежуток 8px.

Текстовые сообщения до 4000 символов, переносы строк, Ctrl/Cmd+Enter для отправки.
Обновление открытого чата каждые 5 секунд, списка каждые 10 секунд.
История — страницы по 50 сообщений, новые страницы читаются последовательно,
без пропусков при большом числе новых сообщений. Список содержит непрочитанный
счётчик; read-cursor продвигается только при фокусе/видимости и прокрутке вниз.
Серверный read-cursor не может ссылаться на сообщение из другого диалога.

Черновики остаются в памяти текущего экрана при переходах между диалогами;
закрытие окна мессенджера, перезагрузка/закрытие страницы их очищают. Ошибка отправки сохраняет текст и
client UUID: повтор после неоднозначного сетевого отказа возвращает уже
сохранённое сообщение. Изменение текста создаёт новую отправку.
Нет вложений, групповых чатов, push-уведомлений или статуса присутствия.

## Доступ и хранение

Сессионная авторизация и существующий CSRF-guard приложения обязательны.
Участник читает/пишет/подтверждает прочтение только собственных диалогов;
чужие и несуществующие UUID дают одинаковый 404. Поиск возвращает только
публичные id, имя, username, avatarUrl, без email/телефона/private sphere data.
Текст отображается как текст React, без HTML/Markdown исполнения.
Поиск и отправка ограничены по пользователю. Ответы API — `Cache-Control: no-store`.

Хранение в настроенном production PostgreSQL, без fallback.
`messenger_conversations` — уникальная упорядоченная пара пользователей;
`messenger_messages` — тело, автор, глобальная последовательность, UUID попытки;
`messenger_reads` — монотонный курсор прочтения участника.
Сервер сериализует отправки в пределах диалога блокировкой его строки, чтобы
курсоры последовательности не опережали commit соседнего сообщения.

## Отдельная миграция

Схема подготовлена в `server/messenger-schema.js`; она не включена в startup.
До установки API возвращает явный 503 `MESSENGER_SCHEMA_REQUIRED`.

1. `node scripts/migrate-messenger.mjs` — read-only target/schema preflight.
2. Получить явное разрешение на создание трёх таблиц в указанной production БД.
3. `node scripts/migrate-messenger.mjs --apply --database=rollapp` — проверить
   target повторно, создать только таблицы и индексы в одной транзакции;
   lock timeout 5s, statement timeout 30s. Без backfill/cleanup пользовательских данных.
4. Повторить read-only preflight и проверку UI с production API.

`npm run test:messenger:production` проверяет реальный PostgreSQL отдельным
локальным API harness: временные участники/сообщения существуют только внутри
BEGIN → ROLLBACK, после завершения проверяется отсутствие временных пользователей.
Схема не инициализируется.

Не отправлять реальные сообщения ради проверки. Для проверки записи нужен
отдельный rollback-only тест после установки схемы. Обычный UI deployment
остаётся в `ROLLAPP_DATABASE_INITIALIZATION=verify` и не устанавливает схему.
