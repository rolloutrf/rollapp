## Передача планирования при каждой отправке

Повторная проверка выполнена на той же базе с незакоммиченной правкой подписей
и удалённым переключателем планирования. Каждый запрос из чата явно передаёт
`includePlanning: true`. Сервер подставляет существующий семидневный снимок
владельца перед обращением к модели. Запросы старых клиентов без этого флага
сохраняют прежнюю семантику. История в запросе ограничена текущей беседой.

Повторно прошли `npm test` (985 прошли, 1 пропущен), `npm run test:ui` и
`npm run build` с предупреждением Vite о размере отдельных чанков.
`npm run test:messenger` прошёл на всех 10 размерах. Сценарий подтвердил
отсутствие переключателя и флаг `includePlanning: true` во всех запросах,
включая продолжение беседы, параллельные чаты и повтор после ошибки. Просмотрены
скриншоты 320×844, 1440×844, 390×400 и 1440×400.

Функция `readAssistantPlanningContext` выполнилась по TLS на настроенном
production PostgreSQL в `BEGIN READ ONLY` → `ROLLBACK`. Случайный UUID владельца
дал пустой снимок за 10–16 ноября 2026 года. Первая отдельная попытка соединения
не загрузила штатный пароль из Lockbox. Повтор загрузил его тем же способом,
что и backend. Схема не инициализировалась, данные не записывались, постоянный
dev-сервис продолжил работу. Запросы к реальному провайдеру и экран после входа
через production API не проверялись.
