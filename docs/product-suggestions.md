# Бесплатные подсказки названий товаров

`ProductTitleInput` — общий владелец поля названия в `WishModal` и
`WishlistBusinessItemEditor` для сферы `products`. Остальные сферы сохраняют
обычный `Input`. Композиция использует установленный shadcn Base UI Combobox,
18/28px для названий вариантов, общий caption для описания и строки от 48 px.
Портал остаётся в управлении Base UI, без отдельного focus trap.

При ручном вводе от 3 до 160 символов через 600 мс отправляется
`POST /api/catalog/product-suggestions` с `{ query }`. POST здесь только чтение:
черновик не включается в URL/access log, API требует авторизацию и существующую
same-origin проверку. Внешнему источнику передаётся только строка поиска,
без пользователя, описания желания или cookies Rollapp.

Источник — [Wikidata Action API](https://www.wikidata.org/wiki/Help:Data_access),
структурированные данные [CC0](https://www.wikidata.org/wiki/Wikidata:Licensing).
Ключ и подписка не нужны. Запросы `wbsearchentities` (ru, максимум 12 результатов)
и затем один пакетный `wbgetentities` проверяют товарные признаки. Фильтр
принимает сведения о производителе P176 либо прямую классификацию P31 как
модель смартфона/компьютера или беговую обувь; исключает прямые классы людей,
организаций, предприятий и служебных страниц. Deprecated claims не учитываются.
Это ограниченный фильтр, не полный обход иерархии Wikidata и не каталог всех
потребительских товаров. Некоторые модели без нужных утверждений пропускаются,
а промышленная продукция с производителем тоже может попасть в результаты.

В интерфейсе явно названа Wikidata и неполное покрытие. Не обещать наличие в РФ,
актуальные цены, размеры, цвет/память, фотографии или полную одежду. Выбор
меняет **только название**; цена, описание, ссылка, фото и публикация остаются
под контролем пользователя. Любое своё название допустимо, в том числе при
пустом ответе, лимите или недоступности источника. Новых полей/таблиц БД нет.

Сервер делает не более 20 новых поисков/минуту на процесс (до 40 последовательных
внешних чтений), один поиск одновременно, одинаковые запросы объединяются.
Иной запрос при занятости получает 429 с Retry-After; очереди старых нажатий нет.
Дополнительно 30 входящих запросов/минуту на пользователя. Это внутренние
консервативные ограничения, не заявленные квоты Wikimedia. Пять минут и до 100
поисков кешируются только в памяти процесса; базу целиком не скачиваем и
поисковый индекс не создаём. Ответы до 2 MB, общий таймаут 8 с, фиксированный HTTPS
host, запрещены редиректы. Ошибки/лимиты не подменяются внутренним каталогом.
Retry-After источника удерживает общий cooldown. При нескольких процессах
бюджет следует координировать; текущий лимит не является распределённым.

Клиент отменяет запрос и игнорирует поздние ответы при изменении строки,
закрытии, отключении поля, размонтировании и IME. Escape закрывает список,
стрелки и Enter выбирают вариант без отправки формы. Нет выбора по умолчанию
или изменения названия при blur. Поиск запускается после ввода, а не открытия
формы или подстановки метаданных. Клиент соблюдает Retry-After без автоповтора.

## Проверки

- `npm test`: в том числе серверные ошибки, фильтр, кеш, бюджет, coalescing,
  аутентификация и валидация read-only маршрута без БД.
- `npm run test:product-suggestions`: восемь размеров от 320 до 1920 px, включая
  короткий desktop 420 px; клавиатура/клик, debounce, ручной ввод, IME-события,
  пустые ответы, ошибки, лимиты, поздние ответы, disabled и внешний сброс.
  Компонент получает детерминированную функцию поиска; все HTTP API обращения
  запрещены. Это не подмена БД и не проверка аппаратной мобильной клавиатуры.
- Реальные формы: `test:business-accounts`, `test:form-actions`, `test:form-pages`,
  `test:drawers`; `check:comprehensive` включает полный release gate.
- Живая проверка модуля — только GET к Wikidata, без сохранения форм в БД.

Ни поставщикам данных, ни пользователям сообщения не отправляются. Платных
подписок, регистраций у операторов и массовых загрузок интеграция не требует.
