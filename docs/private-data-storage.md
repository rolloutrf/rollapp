# Хранение личных данных

Пользовательский контент находится в настроенной production PostgreSQL. В Git допустимы исходники, общие справочники без индивидуальных результатов и синтетические fixtures. Контакты, личные тексты, результаты тестов и анализов, фотографии, экспорты и резервные архивы не являются клиентскими defaults или статическими ресурсами приложения.

## Владельцы данных

- Контакты: существующая таблица `contact_overrides`, из которой API выбирает только строки текущего владельца. `source_order` сохраняет порядок импорта; `NULL` оставляет пользовательские контакты перед импортированными. Поиск, facets, избранное и участники задач используют те же строки. Отсутствующий контакт не восстанавливается из исходников. Удаление оставляет owner-scoped tombstone, чтобы повторный импорт не возвращал запись.
- Анализы: `health_lab_content.content_json` хранит перенесённые структурированные отчёты, динамику и attention items владельца. Новые PDF остаются в `lab_report_uploads`. Общая merge-функция объединяет их с приоритетом новых загрузок; `lab_report_deletions` продолжает скрывать удалённые даты. Пустой аккаунт получает пустые результаты. `server/lab-analytes.js` содержит только общую терминологию, коды, единицы и группы без результатов пациентов.
- Фотографии: `wish_images.image_data`, общий существующий upload/media API и ссылки из профиля/контактов. Контактное фото выдаётся через аутентифицированный owner-scoped маршрут. Git и runtime filesystem не содержат набора аватаров.
- Личные документы: `career_content`, `identity_content`, `identity_report_uploads` и `identity_generated_reports`. Нет персональных Markdown/PDF defaults. Парсеры проверяются на генерируемых синтетических PDF, включая стили, диаграммы и полный текст.
- Архив исходников и прежних версий: `private_files`, с исходным путём, MIME, байтами, размером и SHA-256. Ограничения БД проверяют размер и хеш. `GET /api/me/private-files` показывает список, `GET /api/me/private-files/:id` скачивает файл только владельцу сессии. Shared-profile параметр не даёт доступа; ответы не кешируются. Архив не подключается к shared/public сферам.
- Индивидуальная operational-настройка контакта поддержки хранится в `application_settings`. Runtime загружает её после проверки схемы; явное окружение оператора имеет приоритет. Код содержит только общий адрес продуктового бота. Production redirect smoke выбирает существующий public profile из API, без личного username в workflow.

## Импорт и повторный запуск

`npm run private-data:import -- --username OWNER --source PRIVATE_DIRECTORY` проверяет существующую production-цель и владельца и показывает план. Источники должны находиться вне репозитория. `--apply-schema` — отдельно разрешённое добавление таблиц/колонки, без штатного schema initializer. `--apply` архивирует и проверяет исходные байты, затем материализует данные.

Формат приватного каталога: `contacts.json`, `lab-results.json` (`reports`, `trends`, `attentionItems`), `settings.json`, `files-manifest.json`, исходные файлы в `files/` и `history.bundle`. В Git этот каталог не попадает. Импорт не печатает имена, тексты или байты файлов. Сохранённый архив позволяет получить исходники через закрытый API после удаления локального временного каталога.

Существующие контакты, пользовательские поля, timestamps и tombstones не перезаписываются; меняется только порядок импортированных ID и пустые/прежние файловые ссылки на изображения. Идентификаторы изображений и архивов детерминированы внутри владельца, повторный импорт не создаёт дубликаты. Импортированный baseline анализов вставляется только при отсутствии записи. История и новые загрузки не удаляются.

`npm run contacts:import -- --source PRIVATE_DIRECTORY --username OWNER [--apply]` импортирует Obsidian-контакты непосредственно в PostgreSQL. `npm run contacts:avatars -- --username OWNER [--limit 100] [--refresh] [--apply]` сохраняет загруженные фото в БД и уступает конкурентным правкам. Экспортер review требует явный источник и сохраняет результат только вне репозитория.

Обычный startup/deploy остаётся в `verify`: новые таблицы проверяются через `LIMIT 0`, без DDL/импорта. Отсутствующая схема или PostgreSQL — видимая ошибка. Memory mode доступен только явно выбранным test fixtures с `NODE_ENV=test` и `DEMO_MODE=true`.

## Проверки и история Git

`npm run test:private-data` входит в release gate: запрещает личные storage/archive paths и shared record defaults. `npm run test:private-data:production` проверяет реальную PostgreSQL, целостность байтов, сохранение правок/удалений, повторный импорт, owner isolation и закрытый download API. Все его временные записи находятся в одной транзакции с обязательным `ROLLBACK`, без DDL; отсутствие пользователей после отката проверяется отдельно.

Для очистки истории сначала сохраняется полная история в закрытый архив БД и проверяются байты. Переписывание выполняется в изолированном mirror, сохраняет текущую реализацию и очищает все публикуемые ветки; push использует точные leases на прежние refs. Незавершённые изменения других worktrees не сбрасываются. Старые локальные копии и платформенные PR/cache refs требуют отдельной синхронизации/очистки: их нельзя считать исчезнувшими из-за удаления файлов в HEAD. Не восстанавливать старые ветки поверх очищенной истории.

Несохранённые browser drafts, платёжные intents, TON Connect sessions и Keychain устройства остаются transient-клиентским состоянием по своим действующим контрактам; это не файлы Git и не shared defaults. Очистка репозитория не должна удалять защиту черновиков от потери текста.
