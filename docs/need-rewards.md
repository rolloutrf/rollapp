# Потребности и вознаграждения

## Продуктовая модель

Пользователь выбрал вознаграждение только существующими роллами 1 ноября 2026 года. Расчёты используют существующий баланс PostgreSQL; квитанции выплат и возвратов получают независимые подтверждения существования через OpenTimestamps/Bitcoin. Это гибридный механизм, а не on-chain escrow или новый криптотокен. Кошелёк и криптовалюта пользователю не нужны; вывода в деньги и обещаний доходности нет.

Маховик: человек публикует конкретную потребность → бизнес видит реальный спрос → предлагает решение и обеспеченную награду → получает заказ → человек подтверждает результат и получает роллы → тратит их в сервисе и возвращается с новой потребностью. Заказ и возможность повторной продажи мотивируют бизнес снова выделить бюджет. Это проверяемая продуктовая гипотеза, а не гарантия роста.

Роллы награды — маркетинговый расход бизнеса. Например, при бюджете 1000 роллов можно предложить десять наград по 100. Нельзя отправить одиннадцатый такой оффер без пополнения: бюджет каждого предложения сразу списывается в резерв. После завершения 100 роллов переходят клиенту, без новой эмиссии и комиссии. При отказе или разрешённой отмене они возвращаются бизнесу. Стоимость товара/услуги и условия её оплаты стороны согласуют отдельно; механизм не подтверждает факт денежной оплаты.

Выгоды:

- Пользователь получает подходящее предложение и роллы за полученный результат, а не за просмотры или клики.
- Бизнес получает клиента с явно выраженной потребностью, собственную историю результатов и контроль маркетингового бюджета.
- Сервис получает повторное использование и более полезные предложения. Комиссия пилота — 0. Экономику самого Rollapp этот механизм отдельно не финансирует; платный бизнес-тариф/комиссия потребуют отдельного продуктового решения.

Новые публикации, входы, отправленные офферы, положительные отзывы и приглашения не создают роллы. Приветственная акция и награды за первые желания остаются существующими отдельными программами; их правила здесь не изменяются. Не приписывать новой модели отсутствие общей эмиссии во всём сервисе.

## Поведение

По уточнению пользователя 2 ноября 2026 года механика остаётся серверным слоем: отдельного экрана, входа из кошелька и формы публикации потребности нет. Обычный интерфейс добавления желаний и его обработчики не изменены. Старый адрес `/app/rolls/needs` обрабатывается общим fallback и возвращает к желаниям. API: `/api/need-rewards`; резервирование, переходы, возвраты, история и OpenTimestamps workers сохраняются.

Серверные действия ниже доступны интеграциям через аутентифицированный API. Само создание обычного желания не вызывает этот API и не создаёт новую business-funded награду. Привязка к пользовательским сценариям должна сохранять явное согласие на публикацию и бюджет бизнеса; удаление отдельного экрана не разрешает автоматически публиковать приватные желания или списывать роллы без обеспеченного оффера.

1. Создание потребности через API требует явного согласия пользователя на публикацию всем бизнес-аккаунтам. Приватные документы, здоровье, цели, Wishlist и расшаренные сферы автоматически не импортируются. Публикуемый текст должен обходиться без личных данных.
2. Бизнес видит открытые публикации и свои исторические предложения. Он указывает решение, сроки/цену/условия проверки в тексте и целую награду от 1 до 1 000 000 роллов. При отправке сумма резервируется из его существующего баланса. Нельзя сделать оффер себе.
3. У одной потребности может быть до 10 ожидающих офферов и только один принятый результат. У бизнеса один оффер на потребность; массовая повторная отправка исключена. У пользователя максимум 20 незакрытых потребностей.
4. Оффер действует семь дней. После истечения принять его нельзя; отклонение пользователем или отмена бизнесом возвращает резерв. Фоновый worker раз в минуту возвращает резерв просроченного непринятого оффера; бизнес также может отменить его вручную. Отмена и автоистечение сериализуются одной блокировкой потребности/оффера и освобождают резерв ровно один раз.
5. Принятый оффер переводит потребность в работу. Бизнес может сообщить о передаче результата либо отменить работу с возвратом собственного резерва. После передачи результата односторонняя отмена бизнесом недоступна.
6. Пользователь подтверждает фактически полученный результат. Через семь дней после этого появляется действие «Получить роллы». Получение закрывает потребность и переводит резерв пользователю ровно один раз.
7. До выплаты пользователь может открыть спор с описанием причины. Он блокирует выплату и обычный возврат. Автоматического арбитража и сроков ответа поддержки продукт не обещает. После изучения доказательств оператор отдельно решает выплатить клиенту или вернуть бизнесу; решение и причина остаются в журнале.
8. Остальные офферы пользователь отклоняет, бизнес отменяет. Их резервы не используются для награды победившего предложения. Закрыть незадействованную потребность можно после отклонения/отмены всех офферов.

Собственная статистика показывает полученные награды, резерв бизнеса и число завершённых им результатов. Это не публичный рейтинг и не удостоверение личности. Переговоры, чат, доставка, фиатная оплата и доказательство исполнения находятся вне этого первого механизма.

## Расчёты и доступ

Таблицы `reward_needs`, `reward_need_offers`, `reward_need_entries`, `reward_need_events`, `reward_blockchain_receipts` создаёт отдельный `npm run db:migrate:need-rewards`. Миграция проверяет настроенные database/role и таблицу users, использует TLS, транзакцию и таймауты. Она не меняет существующие балансы, не запускает общий initializer, backfill или очистку данных.

Флаг `ROLLAPP_NEED_REWARDS_ENABLED=true` включает HTTP-действия и историю наград в кошельке. До миграции флаг должен оставаться выключенным. Включённый запуск в `verify` проверяет все используемые столбцы новых таблиц в существующей READ ONLY транзакции. Ошибка не скрывается fallback или миграцией. Выключенный модуль отвечает явным `NEED_REWARDS_DISABLED`, не обращаясь к своим таблицам.

Журнал содержит reserve (минус баланс бизнеса), refund (плюс бизнесу) или reward (плюс пользователю). Для каждого оффера уникальны резерв и единственное освобождение: refund либо reward. Все обновления кошелька, состояния и записи журнала коммитятся одной транзакцией. Поэтому сумма обычных балансов плюс невыплаченные резервы сохраняется, за исключением независимых старых программ начислений/покупок сервиса.

Операции блокируют потребность, затем оффер, затем затрагиваемый кошелёк. Уникальный частичный индекс запрещает два выбранных результата. Ключи публикации и оффера сохраняются до отправки в sessionStorage с привязкой к пользователю; неопределённый сетевой результат повторяется с тем же payload/key. Сервер сверяет всю исходную нагрузку и независимо проверяет пользователя, сумму, время и состояние. Подтверждённые отказы разрешают исправить форму. После успешной записи форма очищается даже при сбое последующего чтения. Действия состояний допускают безопасные повторы без второго перевода.

Обычный пользователь видит только свои потребности и полученные офферы. Бизнес видит явно опубликованный открытый спрос и свои офферы. Чужие предложения, контактные данные и балансы не раскрываются. Издатель публикации и бизнес-отправитель вычисляются по сессии, а не по body. Маршруты используют существующие аутентификацию/CSRF и лимит 20 записывающих запросов в минуту на пользователя. Лента загружается порциями по 50. Периодическое чтение раз в 30 секунд и возврат фокуса обновляют новые офферы, не публикуя ничего автоматически.

## Споры и восстановление

Только после разбора конкретного спора оператор с доступом к настроенной production БД выполняет:

```sh
node scripts/resolve-need-reward-dispute.mjs OFFER_UUID refund "Причина решения после проверки" --apply
# либо outcome reward для выплаты пользователю
```

У HTTP API нет административного варианта этого действия. Команда проверяет точную БД/роль и состояние `disputed`, атомарно освобождает резерв, сохраняет причину с NULL actor (оператор не выдаётся за клиента/бизнес) и не допускает повторной выплаты. Это финансовое решение по конкретной записи, а не штатная часть релиза или проверки. Не выполнять его на настоящих спорах без соответствующего поручения.

При сбое UI закрыть доступ к новым операциям флагом, не удалять таблицы или journal. Отключение флага также приостанавливает получение/возвраты; перед длительной паузой нужен план обслуживания действующих резервов. Возобновление сохраняет все ключи и состояния. Клиентский сбой после коммита лечится чтением и повтором исходного запроса, а не ручным начислением.

## Проверка и выпуск

- `npm test`: валидация согласия, сумм, защищённых полей, переходов, сроков, выключенного API и READ ONLY startup.
- `npm run test:need-rewards`: серверные проверки согласия, валидации, ролей, состояний, сроков и blockchain proof. Отдельный UI и его fixtures удалены; старые 96 UI-сценариев в датированном отчёте относятся к предыдущему кандидату, не к текущей версии.
- `PG_POOL_SIZE=1 npm run test:need-rewards:production`: отдельное соединение к проверенной production БД, новые записи только BEGIN → ROLLBACK; без DDL, инициализации или миграций. Проверяет реальное списание/возврат/выплату, общую сумму, идемпотентность, приватность, авторизацию, раннюю выплату, спор, операторское решение и историю кошелька.
- `npm run check:comprehensive`, `npm audit`, `npm audit --omit=dev` по `docs/verification.md`. Отдельно живое чтение в существующей сессии production API без публикации/оферов/переводов.
- До rollout: миграция отдельно, включённый READ ONLY schema check, полный release suite. Деплой считается выполненным только после exact SHA health и живого просмотра; применение миграции не означает деплой UI.

## Следующие этапы

Пилот измеряет время до релевантного оффера, долю принятых/завершённых, стоимость завершённого результата для бизнеса, долю споров, повторное использование на 7/30 день, реальное расходование наград и повторное участие бизнеса. Само число отправок и общий оборот переводов не считаются успехом. Без этих наблюдений нельзя утверждать, что маховик окупается.

Перед масштабированием нужны проверка бизнесов, выявление связанных аккаунтов и сговора, жалобы/модерация, операционный SLA поддержки и единый сценарий заказа/оплаты. Текущий резерв препятствует необеспеченной эмиссии, но не доказывает реальность внешней сделки и не исключает сговор двух аккаунтов. Не стимулировать положительные отзывы; оценка качества не должна влиять на право получить уже обещанную награду.

При переходе от подтверждений к on-chain расчётам потребуется отдельное решение о контракте, обеспечении роллов и арбитраже. Текущая реализация не переводит балансы в Bitcoin/TON и не превращает роллы в торгуемый токен.


## Блокчейн-квитанции

Каждая выплата/возврат создаёт в той же PostgreSQL-транзакции одну неизменяемую квитанцию и запись очереди. Канонический JSON содержит домен/версию, валюту rolls, ID оффера и участников, сумму, тип операции, время БД и случайную 256-битную соль. Текст потребности, контакты, имя, email, телефон, документы и причины спора в него не включаются. SHA256 этого файла — единственное значение, отправляемое публичным календарям. Случайная соль препятствует угадыванию исходного события по хешу.

`ROLLAPP_REWARD_PROOFS_ENABLED=true` включает отдельный worker. Перед стартом проверяются существующая schema и Python runtime. Успешная запись в календарь имеет статус pending, а не confirmed. Worker получает стандартный .ots proof, затем обновляет его по календарным аттестациям. Подтверждение требует совпадения цепочки операций исходного хеша с Merkle root реального Bitcoin-заголовка, согласия двух заданных обозревателей о canonical block hash/header и как минимум шести подтверждений. Отдельная Bitcoin-нода сервиса не используется: это проверка с доверием к двум внешним обозревателям, а не собственная валидация консенсуса. Участник может скачать JSON/.ots и проверить стандартным клиентом с собственной Bitcoin Core.

Выплата роллов не зависит от доступности календарей. При сбое worker сохраняет существующий proof и повторяет попытку; он не начисляет роллы повторно. Строка очереди берётся через SKIP LOCKED и пятиминутную lease с уникальным token, поэтому процессы не перезаписывают результат более нового владельца. За один tick обрабатывается одна запись; при росте нагрузки потребуется пакетирование/повышение пропускной способности. Задержка подтверждения зависит от календарей/Bitcoin и может составлять часы; SLA не обещается.

Network transport использует только точные HTTPS-origin alice/bob calendar и заданные Blockstream/mempool API, запрещает редиректы, ограничивает время и размер ответов. URL из .ots сам по себе не является разрешением обращения. Python-процесс — только codec: stdin/stdout, без сетевых запросов, файлов, БД или ключей; выполняет операции стандартной библиотеки OpenTimestamps, с ограничениями времени/объёма. Pending commitment может быть длиннее 32 байтов из-за nonce/prefix — его нельзя ошибочно валидировать как SHA256 digest.

Квитанции доступны только участникам оффера через `/api/need-rewards/offers/:id/receipt/json` и `/ots`, с no-store и attachment. Пока proof не готов, `/ots` возвращает явный 409 PROOF_PENDING. API различает queued/pending/confirmed. Квитанция доказывает существование неизменённого файла к моменту блока; она не доказывает качество/реальность услуги, истинность текста JSON, обеспечение роллов криптовалютой или личность эмитента. Файл получают из аутентифицированного HTTPS API Rollapp; отдельной публичной подписи платформы в этой версии нет.

Runtime устанавливается из `server/requirements/opentimestamps.txt`: opentimestamps 0.4.5, python-bitcoinlib 0.12.2, pycryptodomex 3.24.1. Пример локальной подготовки:

```sh
python3 -m venv .runtime-ots
.runtime-ots/bin/pip install -r server/requirements/opentimestamps.txt
# ROLLAPP_OTS_PYTHON=/absolute/path/to/rollapp/.runtime-ots/bin/python в своей игнорируемой конфигурации
npm run test:reward-proofs
```

CI устанавливает тот же runtime перед check:release. Dockerfile устанавливает его в /opt/rollapp-ots, удаляет пакеты сборки, pip и setuptools из образа и запускает codec-тесты при сборке. Регулярный релиз по-прежнему только verify, без миграции. Для отключения сетевых подтверждений достаточно выключить ROLLAPP_REWARD_PROOFS_ENABLED: роллы, готовые квитанции и очередь сохраняются. Не удалять очередь ради восстановления.

Источники протокола и независимой проверки: [OpenTimestamps client](https://github.com/opentimestamps/opentimestamps-client), [официальная библиотека](https://github.com/opentimestamps/python-opentimestamps), [Esplora API](https://github.com/Blockstream/esplora/blob/master/API.md). Денежных транзакций клиента Bitcoin при этом нет: публичные календари агрегируют хеши в собственные blockchain commitments.

Worker автоистечения обрабатывает до 20 кандидатов за минуту, начиная после первого интервала, а не как часть schema/startup cleanup. Принятые/переданные/подтверждённые и оспоренные офферы не отменяются по сроку. При предельном балансе возврат сохраняет резерв и повторяется позднее, не переполняя кошелёк и не блокируя транзакции других кандидатов в своей пачке. Автоистечение записывает системный actor NULL и событие expire.
