пользователя применён описанный ниже шаг восстановления.

## Подтверждено

- Целевая VM: `epdn3osv2a7l82iqoo3v`, внешний IP `51.250.110.17`, состояние `RUNNING`.
- Публичный HTTPS-домен закрывает соединение в curl и браузере из текущей среды.
- Последняя публикация `34688563897` не прошла проверку production после перезапуска.

- Фактические metadata options: GCE endpoint и GCE IAM token включены;

- Полные метаданные (`yc ... get --full`) содержат `docker-compose`,
  `serial-port-enable`, `ssh-keys`. Публичный ключ соответствует локально настроенному

- В Compose указан образ `cr.yandex/crpvg7pqnbpjl26q93f6/rollapp:fe4ecc95025d6cad4000d61dda60c4b94ba3cee3`.

Сбой cloud-init — подтверждённая проблема загрузки; восстановление сайта после её
исправления ещё нужно проверить. Причина зависания интерфейса стороннего Wallet
отдельно не подтверждена.

## Предлагаемый шаг восстановления — требует подтверждения

На указанной VM включить только `aws-v1-http-endpoint`; оставить
`aws-v1-http-token=disabled`, `gce-http-endpoint=enabled`, `gce-http-token=enabled`.
Это позволит текущему cloud-init получить конфигурацию через используемый им
EC2-совместимый канал, не добавляя выдачу IAM credentials через IMDSv1.

IMDSv1 читает метаданные без сессионного токена, поэтому включение канала меняет
границу доступа к служебной конфигурации изнутри VM. Именно по этой причине
действие не выполнено автоматически.

Перед изменением повторно проверить ID, service account, статус и текущие
metadata options. Не менять Compose, диски, сеть, SSH-ключи и данные PostgreSQL.
После изменения выполнить один перезапуск, дождаться завершения cloud-init и
проверить публичный `/api/healthz`. Не повторять перезапуск циклически, если
ошибка сохранится. После получения доступа подготовить постоянное решение
для загрузчика с защищённым каналом метаданных.

## Результат разрешённого изменения

- Повторно проверены ID VM, runtime service account и все четыре metadata options.
- Включён только `aws-v1-http-endpoint`; `aws-v1-http-token` остался выключен,
  обе настройки GCE сохранены.
- Выполнен ровно один перезапуск VM.
- Cloud-init успешно завершился 12 сентября 2026 в 15:59:09 UTC с
  `DataSourceEc2`; прежняя ошибка datasource устранена.
- HTTPS сайта после завершения загрузки пока не восстановился.
- Cloud-init заново создал SSH host keys. Новый ED25519 fingerprint сверен с
  доверенным serial log Yandex Cloud. Для проверки использован отдельный
  temporary known_hosts со строгой проверкой; пользовательский known_hosts не менялся.
- SSH под `koloskof` по-прежнему возвращает `Permission denied (publickey)`.
  Serial log сообщает `no authorized SSH keys fingerprints found for user ubuntu`.
- Текущие `ssh-keys` metadata содержат один публичный ключ без префикса пользователя.
  Он побайтово совпадает с настроенным локальным `.pub`.

После отдельного подтверждения пользователя к той же записи добавлен префикс
`koloskof:` (формат `username:public-key`). Перед применением повторно проверены
ID VM, service account и совпадение ключа с настроенным локальным `.pub`.
Ключ не заменялся; SSH под `koloskof` и `sudo -n` заработали.

## Восстановление приложения

- На корневом диске 39 GiB не осталось свободного места: 100% использования.
  Docker хранил 71 образ общим объёмом 34.25 GB. `yc-container-daemon` не мог
  загрузить ожидаемый образ `fe4ecc…`: `no space left on device`.
- Существующий контейнер `298bc75…` находился в состоянии `Exited (255)`;
  признаков OOM в Docker state нет. Docker и container daemon работали.
- Для освобождения места выбраны 14 старых неиспользуемых образов только
  репозитория Rollapp. Сохранены пять последних ранее загруженных версий,
  включая `298bc75…`, `992eb2…`, `eb0c209…`, и новый `fe4ecc…`.
  Контейнеры, bind mounts Caddy и PostgreSQL не удалялись.
- Очистка завершена: на корневом диске свободно 16 GiB, занято 59% вместо
  100%. Наличие текущего образа и пяти сохранённых версий проверено.
- После освобождения места существующий контейнер запущен. Затем daemon
  автоматически завершил загрузку и переключил приложение на ожидаемый
  `fe4ecc95025d6cad4000d61dda60c4b94ba3cee3`. Повторного перезапуска VM не было.
- 12 сентября около 16:08 UTC публичный `/api/healthz` ответил HTTP 200,
  `ok: true` и ожидаемой версией. Этот маршрут выполняет `SELECT 1` в production
  PostgreSQL; подключение к базе восстановлено.
- Публичный `/tonconnect-manifest.json` пока отвечает HTTP 200 с `text/html`:
  текущая опубликованная версия ещё не содержит TON Connect. Ошибка HTTPS
  устранена, но для кошелька требуется публикация подготовленного кода.

Изолированная версия с 13 файлами TON Connect подготовлена поверх `fe4ecc…`
в `/tmp/rollapp-ton-release-20260912`; остальные незавершённые изменения
рабочей копии исключены. Сборка, аудит shadcn и 11 тестов TON/Vite проходят.
Патч для проверки: `/tmp/rollapp-ton-connect.patch`. Эта сборка ещё не опубликована.

Публикация локального TON Connect остаётся отдельным необходимым шагом:
на публичном домене должны быть доступны новый манифест, иконка и API.
