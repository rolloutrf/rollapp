# Сон и питание

В «Здоровье» после «Анализы», «Спорт», «Препараты» доступны пространства «Сон» (`tab=sleep`) и «Питание» (`tab=nutrition`). У каждого собственная область предоставления доступа. Читатель видит записи и дневные итоги без действий изменения. Сервер использует общий requireSphereReadAccess; изменение разрешено только владельцу, SQL всегда ограничен user_id и tracker.

«Сон» представлен лентой плашек по дням: сегодняшняя сверху появляется автоматически, далее — сохранённые даты от новых к старым. Ни календаря, ни кнопки добавления в этом пространстве нет. На плашках нет отдельных кнопок «Редактировать» и «Удалить». Нажатие на всю плашку открывает форму с закреплённой датой. При наступлении нового локального дня, возвращении фокуса или видимости вкладки сегодняшняя плашка обновляется без перезагрузки. Пустая плашка вычисляется в представлении и не создаёт записи в БД; история содержит реальные сохранённые записи, включая несколько ранее записанных периодов одного дня.

Сон записывается на дату пробуждения: время засыпания, пробуждения, качество 1–5 и заметка. Позднее время засыпания означает переход через полночь. Одинаковые часы не допускаются, чтобы не путать нулевой и суточный сон. Если в истории уже есть несколько периодов одного дня, все периоды отображаются, а итог складывает их длительности; нажатие на плашку открывает первый период дня. Это дневник пользователя без медицинских рекомендаций.

«Питание» работает как дневной To Do: общая с планированием лента PlanningDayRibbon на desktop, мобильная строка Previous/дата с weekday/Next/круглая +, список запланированных и отмеченных приёмов пищи. На desktop есть быстрый composer с Enter (Shift+Enter сохраняет перенос, IME не отправляет), а + открывает полную форму с черновиком названия. На телефоне + открывает общую нативную страницу формы. Выбранный день хранится в URL date, сохраняет owner/tab и не меняется после сохранения, включая быстрое добавление или переключение галочки. Одна вертикальная прокрутка документа охватывает список и действия.

Питание хранит дату, время, тип приёма пищи, название, флаг completed, необязательные калории/белки/жиры/углеводы и заметку. Значения относятся ко всему приёму пищи. Пустое значение означает «не указано», число 0 сохраняется отдельно. Новые записи создаются как запланированные (completed=false); старые записи без флага читаются как уже съеденные, без backfill или миграции. Галочка сохраняется через существующий owner-scoped API; при ошибке прежнее состояние и итоги сохраняются, доступен повтор. Итоги дня по съеденным приёмам пищи суммируют только заполненные значения и показывают «—», если показатель не указан ни разу.

Даты — локальные календарные ключи без UTC-преобразования. Переключение дня в питании не изменяет записи. Формы используют form-surface, мобильную страницу и общий футер; PlanningDatePicker остаётся в питании, а дата сна закреплена за плашкой и показана обычным текстом. Закрытие вложенной даты через Back сохраняет черновик формы; успешный submit возвращает только после ответа сервера. Ошибка сохраняет поля и позволяет повторить. Удаление требует destructive-подтверждения.

## Хранилище

`health_tracker_entries` хранит ID записи, владельца, тип трекера, дату, валидированный JSON и время создания/изменения. Данные живут в настроенном production PostgreSQL, без localStorage или демонстрационной базы. Общие схемы и расчёты находятся в `shared/health-trackers.js`, CRUD — `server/health-trackers.js`.

Для существующей базы отдельно применяется `server/migrations/2026-10-20-health-trackers.sql` после явного разрешения и сверки базы/роли. Она создаёт только новую таблицу и индекс. Обычный запуск/релиз остаётся в `ROLLAPP_DATABASE_INITIALIZATION=verify`: проверяет колонки в READ ONLY транзакции, не запускает миграции. При отсутствии таблицы API возвращает видимую ошибку 503 HEALTH_TRACKER_SCHEMA_REQUIRED. Авторизованная миграция применена 20 октября 2026 к настроенной базе rollapp ролью rollapp_app.

Проверки: `npm run test:health`, `npm run test:health:production`, `npm test`, `npm run check:comprehensive`. Production-проверка создаёт только временные записи в одной транзакции, всегда выполняет ROLLBACK и проверяет их отсутствие после отката. Она не инициализирует схему.
