# Категории бизнес-аккаунтов

При регистрации по email выбор «Бизнес» показывает обязательное поле «Категория бизнеса». Категория не выбрана заранее. Переключение на личный аккаунт очищает её, сохраняя имя, email и пароль. Сервер отклоняет бизнес-регистрацию без известной категории и личную регистрацию с категорией.

| Категория | Ключ | Сфера клиента |
| --- | --- | --- |
| Психолог / Коуч | `psychologist-coach` | Идентичность |
| Доктор | `doctor` | Здоровье |
| Продавец | `seller` | Вишлист |
| Преподаватель | `teacher` | Образование |
| Карьерный консультант | `career-consultant` | Карьера |

Источник соответствий — `shared/business-accounts.js`. Сфера «Карьера» включает существующее пространство контактов с совместимым storage scope. Категория возвращается в `user.businessCategory` при регистрации, входе и чтении сессии; сохраняется в nullable `users.business_category`.

Экран «Клиенты» показывает категорию и её сферу. При запросе сфера фиксирована, а конкретное пространство выбирается из `SPHERE_SECTIONS` этой сферы. Для продавца используется существующий scope `wishlist/wishlist`.

Категория задаёт допустимую сферу запроса, а не автоматическое разрешение читать частные данные. Каждый раздел по-прежнему требует подтверждения владельца. Сервер проверяет категорию при запросе, одобрении, прямой выдаче и чтении раздела, фильтрует кандидатов, входящие разрешения и запросы. Отзыв разрешения остаётся доступен. Публичный вишлист сохраняет обычные правила публичного чтения.

Существующие бизнес-аккаунты с `NULL` сохраняют прежний порядок доступа по согласию. Их категория и разрешения автоматически не изменяются. Неизвестные непустые категории не получают доступ. OAuth/телефонные личные аккаунты не становятся бизнес-аккаунтами автоматически.

## Отдельная операция схемы перед выпуском

Обычный startup/release остаётся в `ROLLAPP_DATABASE_INITIALIZATION=verify`. Он проверяет `users.account_type,business_category` в READ ONLY транзакции; отсутствие столбца останавливает запуск без миграции или demo fallback.

`npm run business:categories:migrate` использует настроенный production PostgreSQL, проверяет совпадение database/role/таблицы `users` и наличие столбца без изменений. TLS используется по умолчанию; SSH-туннель — только при `ROLLAPP_DATABASE_CONNECTION=tunnel`.

Только после отдельного явного разрешения выполнить `npm run business:categories:migrate -- --apply`. Команда в одной транзакции с `lock_timeout=5s` и `statement_timeout=15s` добавляет nullable столбец с ограничением известных категорий и типа аккаунта. Она не запускает общую инициализацию, не меняет существующие аккаунты/разрешения и не делает backfill. Затем повторить проверку существующей схемы и проверить новую регистрацию/вход в согласованном режиме перед rollout.

## Проверки

`npm test` проверяет обязательность категории, тип аккаунта, все соответствия сфер/разделов, legacy-аккаунты и отказ для неизвестных значений.

После отдельно разрешённой миграции `npm run test:business:production` проверяет на точной настроенной production-БД сохранение пяти категорий и ограничения столбца внутри `BEGIN` → `ROLLBACK`. Сценарий не инициализирует схему, не создаёт сессии/кошельки/запросы и проверяет отсутствие временных аккаунтов после отката. Он дополняет, но не заменяет реальную проверку регистрации/входа.

`npm run test:business-accounts` проверяет реальные компоненты выбора типа/категории и пространства на 320, 390, 768, 820, 1024, 1440, 1920 px и 390×400: обязательность, сброс категории, сохранение остальных полей, keyboard/cancel, пять категорий, меню, геометрию, прокрутку и соответствие пространств. Это presentation-проверка без API/БД: все API-запросы запрещены. Сохранение категории в production требует отдельной проверки после разрешённой операции схемы. Проверка входит в `check:release` и `check:comprehensive`.
