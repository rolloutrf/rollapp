# Цифровая визитка

Первый этап переносимых контактов: кнопка «Моя визитка» в собственном разделе
контактов, существующий QR профиля и кнопка «Визитка» в публичном профиле открывают
одну `ContactCardDialog`. Посетитель публичного профиля может скачать визитку
без входа. Просмотр не меняет контакт, профиль, избранное или настройки доступа.

Визитка содержит только явный список полей: `name`, `username`, `url` и
идентификатор формата `rollapp-contact-card`, `version: 1`. `publicContactCard`
из `shared/contact-card.js` собирает новый объект вместо сериализации session.
Email входа, внутренний user id, birthday, bio, заметки, избранное и записи других
контактов не экспортируются. Телефон, компания и социальные ссылки пока не входят
в этот формат; для них нужен отдельный выбор самим владельцем.

QR кодирует URL публичного профиля и строится локально существующим пакетом
`qrcode`. Внешние QR-сервисы не получают URL. Копирование и системное «Поделиться»
передают ту же ссылку; отмена системного окна не считается ошибкой. Если Web Share
недоступен, используется clipboard; его отказ виден и допускает повтор.

Форматы скачивания:

- `.vcf`: vCard 4.0 с `FN`, `NICKNAME`, `URL`; UTF-8, CRLF, экранирование TEXT и
  перенос физических строк до 75 байт без разрыва кодовой точки по
  [RFC 6350](https://www.rfc-editor.org/rfc/rfc6350).
- `.json`: открытая версия 1 с тем же списком публичных полей, для других клиентов.

Файлы формируются в браузере через Blob, object URL освобождается после запуска
скачивания. Имена файлов ограничены безопасными символами. Визитка — снимок на
момент скачивания; URL зависит от текущего домена и username. Экспорт на локальном
preview содержит локальный домен; для внешнего обмена нужен production URL.

Поверхность использует общий Dialog, VisualViewport приложения и ControlBar.
Шапка и нижний ряд Back/«Скачать vCard» находятся вне единственного прокручиваемого
тела. Нижний ряд остаётся доступен на коротком экране. Закрытие возвращает фокус
к открывшей кнопке. Все действия сохраняют общие 48px и радиус 24px.
Размер QR локально ограничен высотой VisualViewport: до 256px на обычном экране,
144px при высоте 400px. Это позволяет прокрутить весь код в видимую область,
не скрывая нижние действия.

## Подпись и TON Testnet

Владелец открывает «Подпись TON Testnet», подключает отдельную временную сессию
Tonkeeper / My Wallet и явно подписывает визитку. Сессия платежного кошелька
Rollapp не переиспользуется и не перезаписывается. Bridge storage находится
только в памяти окна; старый TON Proof не восстанавливается.

Сервер выдаёт одноразовый nonce, привязанный к авторизованному владельцу, текущим
публичным полям профиля, домену и SHA-256 канонического claim. TON Proof проверяет
контроль кошелька; отдельный `signData` text подписывает точный канонический JSON.
Claim содержит `purpose`, версию формата, network `-3`, случайный UUID `cardId`,
номер редакции, `previousHash`, время выдачи и исходную публичную визитку.
Предыдущее значение задаётся загрузкой подписанного файла; обновление требует
того же кошелька и связывает следующую редакцию с предыдущим хешем. Проверка
одного файла не доказывает наличие всех предыдущих редакций.

Проверка обеих Ed25519 подписей извлекает ключ из StateInit распознанного
стандартного v3/v4/v5r1 кошелька и проверяет вычисленный адрес. Ключ, переданный
клиентом, не является источником доверия. Поддержка произвольных/изменяемых
контрактов кошелька отсутствует. TON Proof и signData имеют разные wire layouts;
домен, длины UTF-8, временные окна и связь подписанного текста проверяются явно.
Смена профиля, запрос другого пользователя, повтор nonce/ticket и Testnet/Mainnet
несовпадение завершаются отказом. Nonce/ticket живут в ограниченном Map только
для защиты от replay; restart или другой worker требуют нового подключения.
Это не база данных контактов. Схема PostgreSQL не меняется.

Подписанный `.signed.json` содержит публичные поля, адрес кошелька, StateInit,
публичный ключ и обе подписи. Личные заметки, email и данные других контактов
не включаются. Файл можно проверить кнопкой «Проверить файл» без входа или
полностью офлайн:

```sh
npm run verify:contact-card -- card.signed.json --domain cards.example
```

В примере cards.example заменяется доменом визитки. Для кириллического домена CLI ожидает канонический ASCII host (punycode), который
отображается в подписанном claim, а не произвольное написание адреса. Параметр
`--domain` необязателен. Подпись доказывает контроль ключа в момент подписания;
она не удостоверяет реальное имя, принадлежность аккаунта или текущий статус в сети.

## Реестр Testnet

После подписи пользователь отдельно вводит адрес своего второго Testnet-кошелька
для восстановления. «Подготовить запись» возвращает полный review: адрес
контракта, владельца, восстановления, SHA-256 claim и кода, сумму и срок действия.
Транзакция жёстко ограничена `network: -3`, `from` проверенного подписанта,
StateInit известного контракта и 0,05 тестового TON на баланс реестра. Кошелёк
показывает дополнительную комиссию. Баланс поддерживает хранение; метода вывода
у пилотного контракта нет. Mainnet и автоматическая отправка не предусмотрены.

Контракт `contracts/contact-card-registry.tolk` хранит только SHA-256 cardId,
редакцию, SHA-256 claim, адрес владельца и адрес восстановления. Имена, URL,
визитки и контактные списки не публикуются в контракт. Хеш не является шифрованием.
Код собран Tolk 1.5.0; `npm run build:contact-registry` воспроизводит артефакт.
Сервер перед запуском проверяет соответствие sourceHash и codeHash; Docker
включает и исходник контракта, и артефакт.

Действия контракта:

| Операция | Право | Условия |
| --- | --- | --- |
| UPDATE `0x43415201` | текущий владелец | следующая редакция, ненулевой хеш |
| ROTATE `0x43415202` | текущий владелец | новые owner/recovery различны; pending сбрасывается |
| RECOVER `0x43415203` | recovery | новый владелец, ожидание 604800 секунд |
| CANCEL_RECOVERY `0x43415204` | текущий владелец | отмена ожидания |
| EXECUTE_RECOVERY `0x43415205` | recovery | только после срока ожидания |

UI пилота выполняет первоначальное развёртывание. UPDATE/ROTATE/RECOVER и отмена
проверены в TON Sandbox и доступны через `registryActionBody`; отдельного UI этих
операций пока нет. Подписанное обновление файла сейчас готовит новый реестр для
новой версии; оно не обновляет старый контракт. После ротации нет готового UI
связывания нового подписанта с историей файла. Автообновление чужих контактов,
доставка файлов независимо от Rollapp, импорт в базу и DID не реализованы.

Ответ `sendTransaction` означает только ответ кошелька. «Подтверждено» появляется
после отдельного запроса к фиксированному Testnet RPC, проверки active state,
точного bytecode, cardId, владельца, редакции и хеша. Ошибка RPC не подтверждает
регистрацию. При скачивании после подготовки в файл добавляется advisory locator
`registry`; он не подписан и сам по себе ничего не доказывает. Перед доверием
указанному адресу всегда требуется свежая on-chain проверка. Старый подписанный
файл остаётся исторически действительным даже после изменения состояния реестра.

Реальное подключение, подпись кошельком и деплой в Testnet выполняет владелец.
Локальные тесты не являются внешним аудитом контракта или подтверждением
реального развёртывания. Live review не отправляет транзакций и не меняет БД.

## Проверки

`shared/contact-card.test.js` проверяет allowlist, инъекции vCard, Unicode,
физические UTF-8 строки и безопасные URL/имена файлов в общей unit suite.
`npm run test:contacts` проверяет реальные композиции страницы контактов,
PersistentProfileHero и гостевого PublicProfile на 320, 390, 768, 820, 1024,
1440, 1920px, а также 390×400 и 1440×400; обе темы. Проверяются настоящий download
и содержимое файлов, приватные поля, data URL QR, отсутствие внешних запросов,
clipboard error/retry, Web Share success/cancel, возврат фокуса и точные размеры
контролов. Clipboard и системный Share в fixture эмулируются явно.

`test:contacts` входит в `check:comprehensive`. Проверки не заменяют сканирование
реальным телефоном, импорт в Apple/Google Contacts или системный Share на iOS/Android.
Live review использует production API и только просмотр/отмену без тестовых записей.

`npm run test:contact-cards` входит в `check:release`: реальные HTTP обработчики и
криптография с явно синтетическим wallet transport, девять размеров (320–1920px,
включая два коротких окна). Mainnet rejection, отказ/повтор, подмена подписи,
скачивание, загрузка верного/подменённого файла, цепочка обновления, явная Testnet
транзакция и неподтверждённый RPC. Synthetic wallet никогда не обращается к bridge,
RPC или БД. Серверные unit tests отдельно проверяют nonce, auth/size/no-store,
домен/StateInit/подписи, bytecode reproducibility, все права контракта, seven-day
recovery/veto, bounced messages и положительный/отрицательный RPC matching.
