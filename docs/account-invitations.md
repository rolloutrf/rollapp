# Лимит участников и инвайты

Rollapp допускает до 30 000 личных аккаунтов. Число бизнес-аккаунтов при регистрации не ограничено. Новый аккаунт создаётся через Яндекс ID по одноразовому приглашению. Отправитель вводит email для доставки ссылки. Получатель выбирает Яндекс ID, email которого становится адресом аккаунта Rollapp. Эти два адреса могут отличаться. При каждом запуске регистрации Яндекс снова предлагает выбрать аккаунт и подтвердить доступ к почте. Если Яндекс не передал email, исходная ссылка остаётся доступной для повтора в пределах срока действия. При регистрации можно выбрать личный или бизнес-аккаунт, а для бизнеса — категорию и, если требуется, раздел Вишлиста. В существующий аккаунт можно войти через Яндекс ID, Telegram, телефон или email и пароль. Отправлять приглашения может только пользователь с `users.can_invite`; отдельная миграция назначает это право проверенному профилю `@koloskof`.

`account_invites` хранит только SHA-256 токена. Ссылка уходит на email через настроенный Yandex Postbox. Срок — до 10 суток с создания. База и API отклоняют истёкшие, неотправленные и использованные инвайты. Одновременную регистрацию сериализует advisory lock, затем транзакция проверяет вместимость для личной регистрации и атомарно расходует инвайт. Ошибка доставки оставляет новый инвайт непригодным. Консольная почта недоступна с production-БД.

Приглашение подтверждает одноразовый токен из письма или подписанная ссылка из истории. Полная ссылка открывает «Создать свой Rollapp». Для уже подключённого Яндекс ID есть отдельный вход. Если обычный вход возвращает `INVITE_REQUIRED`, действие «Открыть приглашение» позволяет вставить исходную ссылку и перейти к регистрации. Ссылка проверяется сервером, токен остаётся во фрагменте URL и передаётся при регистрации в теле POST. Если адрес Яндекс ID занят аккаунтом без привязки, Rollapp предлагает подключить Яндекс ID из существующей сессии. Вход в существующий аккаунт оставляет инвайт доступным для создания нового.

В профиле «Новое приглашение» и «История приглашений» оформлены отдельными секциями. История показывает адрес, статус, срок действия отправленной ссылки или дату создания записи. Неудачная или истёкшая попытка видна, пока она остаётся последней отправкой на этот адрес. Записи с действующей ссылкой остаются видимыми, в том числе после неудачного повтора отправки. Копирование и повтор находятся в меню действий соответствующей записи.

«Отправить приглашение» использует общий `DrawerFooter` и остаётся в той же HTML-форме, поэтому Enter и проверка email работают штатно. При пустом поле кнопка недоступна. На телефоне она стоит рядом с «Назад». При ошибке загрузки истории в футере появляется «Обновить историю». Повтор чтения сохраняет введённый адрес. `test:profile` проверяет закрепление на коротких экранах, прокрутку истории, скрытие устаревших попыток, меню, копирование и повтор после ошибки.

«Скопировать ссылку» доступно отправителю у действующих отправленных приглашений, в том числе созданных до появления этой кнопки. Если браузер блокирует буфер обмена, ссылка появляется в поле для ручного копирования. Ссылка из письма и скопированная ссылка используют одну запись, один срок действия и одну регистрацию. Для подписания ссылки нужен настроенный `USER_CREDENTIALS_SECRET`; ротация ключа аннулирует ранее скопированные ссылки, а ссылки в письмах действуют до исходного срока. В БД по-прежнему хранится только хеш токена из письма. Копирование не меняет данные и не отправляет письмо.

«Отправить снова» доступно в истории для последней отправленной, истёкшей или не доставленной записи по каждому адресу. Действие создаёт новый токен и письмо на тот же email. После подтверждения отправки предыдущие действующие ссылки этого отправителя для этого email истекают в той же транзакции, которая активирует новую ссылку. При ошибке отправки прежняя ссылка действует до своего срока. Если получатель успел принять приглашение во время повтора, присланная повторно ссылка истекает. Общий лимит на отправку применяется и к повтору. Запись, зависшая в состоянии отправки дольше двух минут, доступна для повтора после обновления истории. Сервер отклоняет позднее подтверждение зависшей отправки, параллельную отправку тому же адресу и повтор устаревшей записи при наличии более свежего действующего или уже принятого приглашения.

После регистрации участник сразу попадает в приложение. В личном аккаунте кнопка «Получить номер» в настройках профиля открывает экран перекидного табло. Сервер разрешает получение номера и чтение квитанции только личным аккаунтам. При получении он выбирает криптографически случайный свободный номер от `00001` до `30000`, защищает выбор уникальным индексом и записывает его один раз. Повторный запрос возвращает тот же результат. Пока сервер отвечает, табло перелистывает цифры. Разряды останавливаются слева направо, затем над табло разлетается конфетти. Ранее присвоенный номер и результат при включённом уменьшении движения показываются сразу и без конфетти. Ранее выданные номера остаются занятыми. Исходный UUID служит внутренним ключом для ссылок и внешних связей.


Для каждого выбора сохраняется `SHA-256("rollapp-member-v1:" + user_id + ":" + number + ":" + nonce)`. `nonce`, номер и хеш возвращаются владельцу. Только проверенная входящая self-transfer транзакция TON с комментарием `rollapp-member-v1:<hash>` переводит статус в `confirmed`; хеш отправки сам по себе подтверждением не считается. Подписанный BOC сохраняется до отправки и при сетевом сбое повторяется без нового `seqno`. Если `seqno` изменился без найденного подтверждения, запись переходит в `failed` для ручной проверки, без повторного списания. Рабочая очередь берёт один отпечаток за раз и использует advisory lock между процессами.

## Отдельная подготовка production

Обычный dev/release старт использует `ROLLAPP_DATABASE_INITIALIZATION=verify` и не меняет схему. `npm run db:migrate-account-invites` только проверяет точную production-БД, роль, число аккаунтов, наличие `@koloskof` и состояние схемы. После отдельного явного разрешения оператор выполняет `npm run db:migrate-account-invites -- --apply`. Миграция только добавляет таблицы/колонки/ограничения и выдаёт право инвайтов этому профилю. До выполнения миграции `verify` показывает ошибку отсутствующей схемы; приложение нельзя выпускать в состоянии, где регистрация обходит новую проверку.

Для автоматической записи в TON нужен **отдельный уже развёрнутый и пополненный кошелёк V4**, не используемый другими отправителями. Поместите его 24 слова в Yandex Lockbox, задайте `YC_TON_MEMBERSHIP_LOCKBOX_SECRET_ID`, при необходимости `YC_TON_MEMBERSHIP_MNEMONIC_KEY`, обязательный `TONCENTER_API_KEY` и после проверки кошелька `TON_MEMBERSHIP_ENABLED=true`. `server/start.js` загружает секрет в память перед запуском API. Отправляется 0.01 TON на тот же кошелёк на каждый номер; сеть удерживает комиссию. При 30 000 номеров это до 300 TON оборота плюс комиссии, поэтому баланс и стоимость нужно согласовать перед включением. Без настройки сеть не вызывается, а номер остаётся закреплённым со статусом `pending`.

Клиент служебного кошелька останавливает чтение RPC при превышении 1 МиБ
после распаковки и отклоняет перенаправления. До проверки ответа TON SDK
клиент ограничивает число записей дополнительных валют и проверяет
числовой ответ `seqno`. При сбое используется действующий цикл повторов.
[Параметры HTTP-клиента](https://axios.rest/pages/advanced/request-config)

Тест `node --test server/member-ton-anchor.test.js` проверяет RPC через
локальный HTTP-сервер, включая штатное чтение кошелька, номер `seqno`,
подтверждение отправки и отказ при превышении ограничений.

## Проверка

`npm test` проверяет токены, срок, независимость проверки токена от адреса доставки, диапазон, формат и распознавание TON-подтверждения. `npm run test:member-invites` проверяет экраны регистрации, табло и профиля на 320, 390, 768, 820, 1024, 1440 и 1920 px, включая окно высотой 400 px. Браузерный fixture проверяет повтор регистрации по исходному токену, когда Яндекс не передал email, завершение анимации, ведущие нули, ошибку и повтор, а также уменьшенное движение без обращения к серверу. `npm run check:comprehensive` включает этот сценарий. Живые проверка писем, регистрация, присвоение номера, миграция и TON-транзакция требуют настроенного production-доступа и отдельного разрешения на мутации.
