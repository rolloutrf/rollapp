# Восстановление production Rollapp — 1 ноября 2026

Production восстановлен на runtime commit `dbaf5442086643bdfdfe223f2c2396c093d562bb`.
Run [41292382905](https://github.com/rolloutrf/rollapp/actions/runs/41292382905)
завершился success с `verification=none`. Публичный `/api/healthz` подтвердил
`ok=true`, `service=rollapp` и этот точный SHA. Начальный HEAD — тот же dbaf544,
рабочее дерево до начала было чистым. Последующий коммит содержит только отчёт
и уточнение эксплуатационного регламента; runtime-код не менялся.

## Подтверждённые причины

VM `fv4chl6pdb4lnhsj7139`, folder `b1gebpfrhvkd43r38q98`, runtime SA
`ajers2ngi708sf3i1t4g`, IP `130.193.58.26` повторно сверены с Cloud API.
Работал старый контейнер05264a5 при декларации более новой версии.

* Системный раздел20GB был заполнен: доступно0 байт. Серийная консоль показала
  `systemd-journald: No space left on device`; отфильтрованные записи контроллера
  также содержали99 совпадений этой ошибки. Docker хранил13 образов, один
  использовался; `docker system df` показывал14.89GB reclaimable.
* Security group разрешала SSH только с прежнего адреса оператора `/32`.
  Для текущего адреса владельца добавлено точечное `/32` правило, существующий
  SSH-ключ и строгая проверка host key сохранены. Прямой SSH после этого работает.

## Подготовка и доступ

Снимок системного диска для отката: `fd8b1m7hutqn10ilv6bu`, READY, в production
folder. Это снимок диска VM; PostgreSQL находится отдельно и не изменялся.
CLI по умолчанию был настроен на другой каталог: первоначальный служебный снимок
из него удалён, корректный production-снимок создан и проверен. Дальнейшие создания
ресурсов использовали явный production folder. Глобальный CLI-профиль не менялся.

Временно использовались вспомогательные VM в соседней зоне с доступом только
от оператора, без runtime service account. Рабочий служебный канал — SSH внутри
TLS: TLS-сертификат и SSH host key сверены с аутентифицированным Cloud serial API;
приватный ключ владельца не переносился на вспомогательные VM. Для внутреннего
SSH временно добавлялось отдельное правило `/32` служебного узла.

Настройка авторизации серийной консоли основной VM временно переключалась на
существующий ключ владельца, затем возвращена к исходному `OS_LOGIN`.
Новые пользователи/ключи основной VM не создавались. Вспомогательные VM, их
автоудаляемые загрузочные диски, неиспользованная отдельная копия диска и
служебная security group удалены. Временное правило доступа служебного узла
удалено. В production остались прежние две VM и два исходных диска; резервный
снимок сохранён. Неиспользованные временные OS Login credentials удалены.
