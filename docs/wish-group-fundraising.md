# Сбор роллов для группы товаров

В шапке открытой группы товаров (`space=products`) вместо количества желаний
показана сумма «Собрано … роллов». Данные загружаются при открытии группы и
используются в шторке «Сбор роллов», которую открывает иконка монет. После
подтверждённого взноса сумма обновляется в обоих местах. Для группы без сбора
показано «Собрано 0 роллов», при ошибке загрузки — «Сумма недоступна».
Владелец может организовать один сбор,
задать целую цель от 1 до 1 000 000 000 роллов, изменить её (не ниже уже
собранной суммы) и возобновить ранее приостановленный сбор. Сумма и количество
уникальных участников показаны в шторке. Достижение цели останавливает
новые взносы; изменение цели вверх снова разрешает их, если сбор не приостановлен.
Цель задаётся явно: рублёвые цены товаров не конвертируются в роллы.

Участник с доступом к группе подтверждает взнос в пределах своего баланса и
остатка до цели. Роллы сразу переводятся в кошелёк владельца без комиссии и
появляются в обычной истории переводов с комментарием `Сбор «Название»`.
Владелец не переводит средства самому себе. Гостю предлагается вход.
Шторка открывается снизу до 768px и справа от 768px. Шапки группы и шторки
используют общий прозрачный фон панелей Rollapp. Шапка с кнопкой закрытия
остаётся видимой при прокрутке содержимого. Кнопки сбора и эмулятора карты
расположены в общем нижнем `DrawerFooter` за пределами прокручиваемой области.
Ссылка на «Финансы» находится в сведениях о выпущенной карте.
Кнопки отправки связаны со своими формами, поэтому работает Enter в поле.
Подтверждение взноса открывается
поверх шторки. После закрытия шторки сохраняется прокрутка группы, а фокус
возвращается на иконку. Поля и кнопки используют общие Field/Input/Button/ControlBar,
Geist 18/28 и подписи 13/16. Все основные действия имеют высоту от 48px.

Сервер проверяет принадлежность группы списку, product-space, доступ к списку
(public / followers / link с точным share token / явный business grant) и хотя бы
один доступный активный товар. Приватные группы не раскрываются посторонним;
владельцу доступны собственные группы. Endpoint не принимает получателя или
собранную сумму от клиента. Идентификаторы и балансы участников не публикуются.

`wish_group_fundraisers` хранит цель/состояние, `wish_group_contributions`
связывает взнос с существующей `roll_transactions`. Списание, зачисление,
запись взноса и проверка остатка выполняются в одной транзакции. Блокировки
группы/списка сериализуют приём с изменением цели, перемещением и удалением;
существующая функция переводов блокирует кошельки в общем порядке. Ошибка
баланса/лимита/доступа откатывает всю операцию. Повтор UUID возвращает прежний
результат, в том числе после приостановки или достижения цели; иной payload с
тем же UUID отклоняется.

Перед отправкой браузер сохраняет сумму и UUID в sessionStorage с ключом
пользователя/группы. При неизвестном результате (сеть, 5xx, 408, 429) доступны
повторная проверка и восстановление после reload с тем же UUID. Известный
отказ 4xx на первой попытке завершает её. Поздний отказ доступа/сессии после
неизвестного результата сохраняет прежний UUID: он не доказывает, что первый
перевод не состоялся. При недоступном sessionStorage перевод не отправляется.

Перемещение сохраняет сбор по ID группы. В других категориях интерфейс и
приём взносов недоступны. При расформировании группы/удалении списка её связь
со сбором обнуляется; сам сбор, все взносы и переводы остаются в журнале.
Это не отмена и не возврат уже выполненных переводов. Автоматического возврата,
escrow и конвертации в реальные деньги в этой версии нет.

## Отдельная операция схемы

Обычный startup/deploy остаётся в `ROLLAPP_DATABASE_INITIALIZATION=verify`.
Отсутствующая схема возвращает для сборов явный 503
`FUNDRAISING_SCHEMA_REQUIRED`, без demo fallback и миграции при HTTP-запросе.

Без записи проверить точную настроенную production-базу/роль и существующие колонки:

```sh
node scripts/wish-group-fundraising-database.mjs
```

Только после отдельного явного разрешения на создание двух таблиц и индекса:

```sh
node scripts/wish-group-fundraising-database.mjs --apply
```

Операция использует проверенную production-конфигурацию и TLS; не вызывает
`initializeDatabase`, backfill, очистку резервирований или изменение текущих
данных. Lock timeout — 5 секунд. Повтор не создаёт вторые таблицы.

## Проверка

`npm run test:wish-groups` включает прежние проверки карточек групп и новую
восьмиразмерную component fixture (320, 390, 767, 768, 820×450, 1024, 1440,
1920). Она проверяет открытие и закрытие шторки, возврат фокуса и прокрутки,
сумму в шапке до открытия шторки и после взноса, загрузку и повтор после ошибки,
цель/паузу, ограничения, подтверждение/отмену, потерю ответа и
восстановление после перезагрузки, состояния гостя, завершённого и закрытого сбора,
ошибки, геометрию и достижимость последнего товара. Проверяются нижний футер
в пустом и заполненном состояниях, его положение при прокрутке и Enter для
создания сбора. На 390px дополнительно
имитируется клавиатура со смещённым VisualViewport. Все HTTP API-запросы во fixture запрещены. Локальный transport
проверяет только UI и не подтверждает работу PostgreSQL.

`npm run test:fundraising:production` использует уже существующую схему
настроенного PostgreSQL. В одной транзакции создаёт временные тестовые сущности,
проверяет endpoints, атомарный перевод, UUID replay/conflict, лимиты, доступ,
завершение и сохранение журнала после удаления группы. Весь набор изменений
откатывается; DDL/инициализация не запускаются. Он не доказывает поведение двух
параллельных браузеров и настоящей мобильной клавиатуры.

## Виртуальная карта: эмулятор провайдера

Владелец может выпустить виртуальную карту сразу после открытия сбора, даже
при нулевой сумме. Кнопка выпуска занимает место действия «Приостановить».
Для ранее приостановленных сборов доступно «Возобновить».
`FundraiserVirtualCard` использует отдельный browser-provider из
`src/lib/virtual-card-emulator.js`: выпуск одной карты на аккаунт/сбор,
тестовый начальный баланс в размере собранных роллов, подтверждение покупки,
проверка остатка и история. При повторном открытии сбора новые взносы
увеличивают тестовый баланс с учётом пробных покупок. Повтор выпуска
возвращает ту же карту; повтор покупки с тем же ключом не списывает повторно.
Гостям и участникам действие выпуска не показывается.

В «Финансах» кошелёк показывает выпущенные карты в разделе «Карты сборов»
с названием группы, идентификатором и тестовым балансом. Ссылка в карте
открывает тот же кошелёк по `/app/rolls`. Старые карты сохраняют остаток и
историю; название группы добавляется при следующем открытии сбора.

Это явно обозначенный тестовый режим без банковских реквизитов и реальных
платежей. Реальные роллы остаются в кошельке владельца; никакого курса к рублю
или резервирования средств нет. Эмулятор не делает запросов к платёжному API
и не подменяет production-базу сборов. Состояние хранится в `sessionStorage`,
разделено по аккаунту и сбору и переживает перезагрузку в текущей вкладке.
Закрытие вкладки завершает тестовую сессию; синхронизации между устройствами
нет. Ошибка чтения/записи видна пользователю, выпуск не получает временного
fallback. Эти клиентские проверки не являются авторизацией реальных денег.

Проверка `npm run test:wish-groups` включает выпуск с нулевым балансом,
переход в «Финансы», отказ по остатку, отмену/подтверждение покупки,
восстановление карты/истории после reload,
отсутствие финансовых HTTP-запросов, ошибку хранилища и геометрию на восьми
ширинах. Unit-проверки провайдера входят в `npm test`.
Для подключения реального провайдера требуется серверная авторизация,
постоянное хранение, резервирование/списание средств, идемпотентные операции
и сверка результатов провайдера; текущий эмулятор не использовать для этого.
