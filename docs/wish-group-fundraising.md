# Сбор роллов для группы товаров

В открытой группе с `space=products` владелец может организовать один сбор,
задать целую цель от 1 до 1 000 000 000 роллов, изменить её (не ниже уже
собранной суммы), приостановить или возобновить приём. Сумма и количество
уникальных участников показываются над товарами. Достижение цели останавливает
новые взносы; изменение цели вверх снова разрешает их, если сбор не приостановлен.
Цель задаётся явно: рублёвые цены товаров не конвертируются в роллы.

Участник с доступом к группе подтверждает взнос в пределах своего баланса и
остатка до цели. Роллы сразу переводятся в кошелёк владельца без комиссии и
появляются в обычной истории переводов с комментарием `Сбор «Название»`.
Владелец не переводит средства самому себе. Гостю предлагается вход.
Интерфейс использует обычный поток внутри существующего диалога группы,
его единственный вертикальный scroller, общие Field/Input/Button/ControlBar,
Geist 18/28 и caption 13/16. Все основные действия имеют высоту от 48px.

Сервер проверяет принадлежность группы списку, product-space, доступ к списку
(public / followers / link с точным share token / явный business grant) и хотя бы
один доступный активный товар. Приватные группы не раскрываются посторонним;
владельцу доступны собственные группы. Endpoint не принимает получателя или
собранную сумму от клиента. Идентификаторы и балансы участников не публикуются.

`wish_group_fundraisers` хранит цель/состояние, `wish_group_contributions`
связывает взнос с существующей `roll_transactions`. Списание, зачисление,
запись взноса и проверка остатка выполняются в одной транзакции. Блокировки
группы/списка сериализуют приём с изменением цели, перемещением и удалением;
существующая функция переводов блокирует кошельки в общем порядке. Ошибка
баланса/лимита/доступа откатывает всю операцию. Повтор UUID возвращает прежний
результат, в том числе после приостановки или достижения цели; иной payload с
тем же UUID отклоняется.

Перед отправкой браузер сохраняет сумму и UUID в sessionStorage с ключом
пользователя/группы. При неизвестном результате (сеть, 5xx, 408, 429) доступны
повторная проверка и восстановление после reload с тем же UUID. Известный
отказ 4xx на первой попытке завершает её. Поздний отказ доступа/сессии после
неизвестного результата сохраняет прежний UUID: он не доказывает, что первый
перевод не состоялся. При недоступном sessionStorage перевод не отправляется.

Перемещение сохраняет сбор по ID группы. В других категориях интерфейс и
приём взносов недоступны. При расформировании группы/удалении списка её связь
со сбором обнуляется; сам сбор, все взносы и переводы остаются в журнале.
Это не отмена и не возврат уже выполненных переводов. Автоматического возврата,
escrow и конвертации в реальные деньги в этой версии нет.

## Отдельная операция схемы

Обычный startup/deploy остаётся в `ROLLAPP_DATABASE_INITIALIZATION=verify`.
Отсутствующая схема возвращает для сборов явный 503
`FUNDRAISING_SCHEMA_REQUIRED`, без demo fallback и миграции при HTTP-запросе.

Без записи проверить точную настроенную production-базу/роль и существующие колонки:

```sh
node scripts/wish-group-fundraising-database.mjs
```

Только после отдельного явного разрешения на создание двух таблиц и индекса:

```sh
node scripts/wish-group-fundraising-database.mjs --apply
```

Операция использует проверенную production-конфигурацию и TLS; не вызывает
`initializeDatabase`, backfill, очистку резервирований или изменение текущих
данных. Lock timeout — 5 секунд. Повтор не создаёт вторые таблицы.

## Проверка

`npm run test:wish-groups` включает прежние проверки карточек групп и новую
восьмиразмерную component fixture (320, 390, 767, 768, 820×450, 1024, 1440,
1920): создание/цель/пауза, ограничения, подтверждение/отмена, потеря ответа и
reload, public/closed/completed/error, геометрия, typography и достижимость
последнего товара. Все HTTP API-запросы во fixture запрещены; локальный transport
проверяет только UI и не подтверждает работу PostgreSQL.

`npm run test:fundraising:production` использует уже существующую схему
настроенного PostgreSQL. В одной транзакции создаёт временные тестовые сущности,
проверяет endpoints, атомарный перевод, UUID replay/conflict, лимиты, доступ,
завершение и сохранение журнала после удаления группы. Весь набор изменений
откатывается; DDL/инициализация не запускаются. Он не доказывает поведение двух
параллельных браузеров и настоящей мобильной клавиатуры.
