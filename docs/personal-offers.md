# Персональные офферы бизнеса

Каталог бизнес-аккаунтов открывается рядом с аватаром в каждой личной сфере.
Сфера определяет категорию бизнеса. Подписка использует существующую связь
`follows` и позволяет бизнесу отправлять предложения. Доступ к личному
разделу выдаётся отдельно через настройки каталога. Отписка прекращает
отправку новых предложений на основании подписки.

Продавец Вишлиста использует кнопку «Предложить» и выбирает подписчика или
покупателя с ранее выданным доступом. Покупатель оплачивает предложение в
Вишлисте или в «Роллах». Для оплаты требуется действующая подписка либо
доступ, опубликованный товар и подходящая категория продавца.

Если собственных товаров ещё нет, бизнес добавляет название, описание, тип
(товар/услуга) и сферу на странице «Клиенты». Создаётся собственная позиция
`business_marketplace_items` в разделе предложений (`store`), с явно заданной базовой ценой в роллах.
Она становится доступна для рекомендаций; обычная покупка магазина не включается.
Повтор сохранения с тем же UUID не создаёт вторую позицию.

Бизнес выбирает свой активный товар/услугу на странице «Клиенты» или в карточке
предложения, получателя из списка подписчиков, цену в целых
роллах (1–1 000 000) и срок (1 час, 24 часа, 3, 7 или 30 дней). Сервер принимает
срок от 1 до 720 целых часов. Создание счёта не резервирует и не списывает роллы.

Таблица `business_personal_offers` сохраняет владельца, получателя, товар,
снимок названия и цены, время создания/истечения и ключ повторного запроса.
Повтор создания с тем же ключом возвращает тот же счёт без продления срока;
другие условия с тем же ключом отклоняются. Выставить счёт себе или от чужого
товара нельзя. Выбор товара использует `business_marketplace_items`, а не
пользовательские желания или предложения внешних маркетплейсов.

В разделе «Предложения» каталога видны счета этой сферы. В кошельке «Роллы»
обе стороны видят все свои счета: активный/ожидает оплаты,
оплачен, срок истёк. Оплата требует явного подтверждения и доступна только
назначенному получателю. Срок отображается в часовом поясе устройства.
Сервер использует собственные часы PostgreSQL. Неиспользованный счёт истекает
по времени: фоновое удаление и очистка не нужны, запись сохраняется в истории.
Счета загружаются страницами по 100 с кнопкой «Показать ещё счета».
Порядок стабилен при одинаковом времени создания (дополнительно по UUID).
После открытия следующих страниц список не схлопывается от фонового обновления;
возврат к свежему списку выполняется кнопкой «Обновить счета». Истечение продолжает
проверяться по времени, а оплата старой страницы сразу меняет её статус.

Оплата выполняется в одной транзакции PostgreSQL: блокировка счёта, перевод
роллов получателя бизнесу через существующий журнал `roll_transactions`, запись
заказа `roll_store_purchases` и привязка заказа к счёту. Цена берётся из счёта,
а не из клиента или изменившегося каталога. Кошельки блокируются в общем
порядке идентификаторов. Срок проверяется до перевода и повторно после ожидания
блокировок через `clock_timestamp()`; ошибка откатывает все изменения.
Повтор оплаты возвращает прежний заказ. Недостаток средств/лимит кошелька
продавца оставляют счёт неоплаченным. Исходный товар не резервируется по складу.

Персональные покупки запрещены к обычному самостоятельному возврату:
существующий возврат магазина начисляет деньги покупателю без списания с бизнеса.
Для возврата такого заказа требуется отдельный сценарий продавца. Автоматическая
доставка, внешний платёжный провайдер и уведомления вне приложения не добавлялись.

## Подготовка production-схемы

Обычный startup/deploy остаётся в `ROLLAPP_DATABASE_INITIALIZATION=verify`.
Не запускать общую инициализацию, миграции других таблиц или backfill.

`node scripts/personal-offers-schema.mjs --check` проверяет конфигурацию и
точные database/role, выполняет только SELECT в read-only транзакции.

После **отдельного разрешения** на production-миграцию:

```sh
node scripts/personal-offers-schema.mjs --apply rollapp rollapp_app
```

Команда проверяет точный target и создаёт только новую таблицу и её индекс
по `personalOffersSchema` в `server/personal-offers.js`, без удаления и изменения
существующих записей. Лимит ожидания блокировки — 5 секунд, statement — 15 секунд.
Она не вызывается автоматически при запуске приложения.

## Проверка

- `npm test`: условия, доступ, идемпотентность, серверное время, замороженная цена,
  запрет повторного списания, обе проверки срока; без БД.
- `npm run test:offers`: восемь viewport, реальный React/CSS и Chrome, отмена,
  повтор после ошибки с неизменным ключом, ошибка баланса и повтор оплаты,
  оплаченные/истёкшие состояния и композиции настоящих BusinessAccessPage/
  RollsWallet, 24px page-stack и semantic h2; все реальные API-запросы запрещены.
- `npm run test:offers:production`: только существующая настроенная production
  PostgreSQL; временные записи в общей транзакции с обязательным ROLLBACK,
  без инициализации схемы. Проверяет точный перевод/заказ, условия, доступ,
  истечение, нехватку средств, повтор и запрет неверного возврата. Список
  дополнительно проверяется на 102 записях, одинаковом created_at, двух страницах
  без потерь/дубликатов и доступе постороннего пользователя.
- `npm run check:comprehensive`: полная существующая матрица, включая новый smoke
  в `check:release`.

Реальные пользовательские счета/оплаты не создаются проверками.
Конкурентная оплата из независимых соединений и фактическая поставка товара
требуют отдельной проверки; последовательный rollback-тест не доказывает гонки.

При совмещении с production main добавлена совместимая ссылка wishlist_item_id в согласованную таблицу business_personal_offers. Старый item_id сохранён, допускается ровно один источник товара. Таблицы Wishlist не изменялись.
